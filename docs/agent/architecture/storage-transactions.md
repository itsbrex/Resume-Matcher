# Storage transaction boundaries

`Database._write_session()` issues SQLite `BEGIN IMMEDIATE` before reads used by a compound write. This serializes writers across connections and processes. Callers commit the entire operation; a raised exception closes and rolls back the transaction. Ordinary read-only queries remain concurrent under WAL. The configured SQLite busy timeout bounds lock acquisition.

- Creating a replacement master demotes the old failed/processing master and inserts the replacement in one transaction. The demotion is flushed before the insert to respect the partial unique index, but it is not committed separately. A failed insert preserves the prior master. An actively processing master may be replaced; its in-flight completion targets its original resume ID and must not restore a cached master flag. The old row stays demoted. A ready or pending master is retained when another upload arrives; subsequent designation changes use `set_master_resume()`.
- `create_jobs()` writes an entire job-description batch in one transaction. The upload route validates every trimmed description before invoking it. Validation or storage failure cannot leave a prefix of the batch persisted; successful IDs retain input order.
- Tracker create, move, delete, and bulk operations reserve the writer before counting positions or reading siblings. Position allocation and renumbering therefore share the same serialization boundary. The independent `(job_id, resume_id)` constraint retains deduplication semantics.
- Each transition from `saved` to any non-saved status fills a missing `applied_at` date. Existing user-supplied dates and an explicit null in the same individual patch are respected. Moves between non-saved statuses do not refill a manually cleared date or erase a previous date. Returning to `saved` and applying again starts another application transition and fills the date only if still missing. Single and bulk moves use the same rule; no implicit first-application history is stored.

Regression coverage: `tests/integration/test_storage_atomicity.py` injects failures at real ORM inserts, holds allocations while competing writers run, checks shared-file database instances, and exercises API validation with real SQLite. Tests use temporary storage and synthetic content.
